# Market Project — актуальный рабочий бриф для новых чатов

## 1. Что это за проект

Это мой Java / Spring Boot multi-module проект, который я хочу довести до уровня **уверенного production-style backend проекта**, а не просто учебного pet-проекта.

### Текущая идея проекта
Проект похож на e-commerce / market platform и сейчас состоит из нескольких модулей:

- `api-gateway`
- `auth-module`
- `user-service`
- `product-service`
- `eureka-server`
- `common`
- `identity-domain`
- `frontend`
- дополнительные служебные / demo-модули

### Технологии, которые уже используются

## 5. Главный архитектурный поворот, который уже принят

Это очень важно учитывать во всех новых чатах.

### Мы больше не строим локальный auth-центр
Принято решение, что:

- **Keycloak** отвечает за identity / authentication / credential lifecycle
- локальный backend **не должен** дальше развивать старый `signin / refresh / logout` как основную auth-модель
- email verification, password reset и credential lifecycle — это зона ответственности Keycloak, а не локальных модулей

### Новая архитектурная идея
Теперь проект движется к модели:

- `Keycloak` — identity provider
- `auth-module` — тонкий identity/account-provisioning слой
- `Account` — локальная доменная сущность пользователя магазина
- `Company` — отдельная **опциональная** бизнес-сущность
- `user-service` — слой профиля и пользовательских бизнес-данных

То есть старая модель `User`, которая совмещала в себе auth, password, компанию и бизнес-логику, больше не считается хорошей целевой моделью.

## 6. Новая целевая модель домена

### Базовая идея
Нужно перейти от старой схемы:

`User + password + role + company`

к новой:

`Keycloak identity -> local Account -> optional Company`

### Что это означает

#### Keycloak хранит:
- логин
- пароль
- email verification
- forgot/reset password
- сессии
- access/refresh lifecycle
- auth/roles/claims

#### Local Account хранит:
- `publicId`
- `keycloakUserId`
- `email`
- поля профиля
- `accountType`
- `status`
- связи с бизнес-сущностями магазина

#### Company хранит:
- информацию о продавце / организации
- ИНН
- название
- контактные данные
- статус проверки / модерации
- связь с владельцем-аккаунтом

### Важное правило
**Company не является обязательной частью любого Account.**

То есть:
- обычный покупатель может жить без `Company`
- продавец получает `Company` позже, в отдельном seller/business flow

## 7. Что уже решено по security и Keycloak

### Общий принцип
Принято решение использовать **Keycloak как единственный identity/auth слой**, а backend-сервисы делать **OAuth2 Resource Server**.

### Что это означает practically
- пользователь логинится **не в локальный backend**, а через Keycloak
- в браузерном сценарии frontend / gateway инициирует redirect на Keycloak
- после логина клиент получает access token
- gateway может быть единой внешней точкой входа и прокидывать token дальше
- **каждый backend-сервис, который принимает пользовательские HTTP-запросы, сам валидирует JWT**
- мы **не строим схему**, где только один сервис валидирует токен, а остальные слепо доверяют заголовкам

### Важный вывод
`api-gateway` не должен быть единственным охранником, которому все остальные сервисы безусловно доверяют.

Правильная модель:
- gateway — входная точка, маршрутизация, возможный token relay
- каждый backend-сервис — самостоятельный resource server

## 8. Что уже решено по `auth-module`

### Почему модуль пока оставляем
Принято решение **не удалять `auth-module`**, а оставить его как заготовку будущего identity/account-provisioning слоя.

То есть оставляем его не ради маленького кода, а ради отдельной ответственности.

### За что отвечает `auth-module`
- current identity context
- связка `Keycloak user -> local Account`
- внутренний provisioning локального `Account`
- технические account / identity use-case’ы

### Что оставляем публично в `auth-module`
На текущем этапе публично оставляем только:

- `GET /api/v1/auth/me`

Этот endpoint нужен для того, чтобы по уже валидному Keycloak JWT понять:
- кто сейчас вошёл
- есть ли под этого пользователя локальный `Account`

### Что НЕ считаем долгосрочно правильным публичным API
Не считать целевыми:

- `signin`
- `refresh`
- `logout`
- `activate`
- `forgotPassword`
- `resetPassword`
- публичный `/me/sync`

### Почему `/me/sync` не считаем правильным
Потому что создание / синхронизация локального account — это **внутренняя серверная механика**, а не отдельное пользовательское действие.

Правильная идея:
- публично есть `GET /me`
- внутри backend есть что-то вроде `getOrCreateCurrentAccount(jwt)` для use-case’ов корзины, заказов, профиля и другой бизнес-логики

---

## 9. Что уже решено по `user-service`

### Новая роль `user-service`
`user-service` не должен дублировать `auth-module`.

Его зона ответственности:
- профиль пользователя
- пользовательские бизнес-данные
- расширенный customer context
- в будущем адреса, настройки, личный кабинет, seller/customer profile сценарии

### Важное разграничение
#### `auth-module /auth/me`
Это endpoint про:
- identity context
- факт существования локального `Account`
- базовую связку Keycloak identity с local Account

#### `user-service /users/me`
Это должен быть endpoint про:
- профиль
- пользовательские данные приложения
- бизнес-представление пользователя

### Критическое правило
Нельзя допускать, чтобы `auth-module` и `user-service` превратились в два одинаковых сервиса с одинаковым `/me`.

## 11. Рекомендуемая целевая структура по сервисам

### `api-gateway`
- единая внешняя точка входа
- маршрутизация
- при необходимости token relay
- не единственный security-проверяющий слой

### `keycloak`
- identity provider
- authentication / authorization
- verify email / password reset / credential lifecycle

### `auth-module`
- current identity context
- `GET /api/v1/auth/me`
- внутренний provisioning локального `Account`
- связка `Keycloak user <-> local Account`
- возможно future first-login / onboarding / account linking logic

### `user-service`
- профиль пользователя
- пользовательские данные
- business/customer context
- в будущем адреса / настройки / кабинет / seller/customer flows

### `product-service`
- каталог товаров
- категории
- карточки товаров
- дальше product ownership / management

### Другие HTTP-сервисы
Если сервис принимает пользовательские запросы и принимает решения по доступу, он должен быть resource server и сам валидировать JWT.
