## 5. Главный архитектурный поворот, который уже принят

Это очень важно учитывать во всех новых чатах.

### Мы больше не строим локальный auth-центр
Принято решение, что:

- **Keycloak** отвечает за identity / authentication / credential lifecycle
- локальный backend **не должен** дальше развивать старый `signin / refresh / logout` как основную auth-модель
- email verification, password reset и credential lifecycle — это тоже зона ответственности Keycloak, а не `auth-module`

### Новая архитектурная идея
Теперь проект движется к модели:

- `Keycloak` — identity provider
- `Account` — локальная доменная сущность пользователя магазина
- `Company` — отдельная **опциональная** бизнес-сущность

То есть старая модель `User`, которая совмещала в себе и auth, и password, и компанию, и бизнес-логику, больше не считается хорошей целевой моделью.

## 6. Новая целевая модель домена

### Базовая идея
Нужно перейти от старой схемы:

`User + password + role + company`

к новой:

`Keycloak identity -> local Account -> optional Company`

### Что это означает

#### Keycloak хранит:
- логин
- пароль
- email verification
- forgot/reset password
- сессии
- access/refresh lifecycle
- auth/roles/claims

#### Local Account хранит:
- `publicId`
- `keycloakUserId`
- `email`
- поля профиля
- `accountType`
- `status`
- связи с бизнес-сущностями магазина

#### Company хранит:
- информацию о продавце / организации
- ИНН
- название
- контактные данные
- статус проверки / модерации
- связь с владельцем-аккаунтом

### Важное правило
**Company не является обязательной частью любого Account.**

То есть:
- обычный покупатель может жить без `Company`
- продавец получает `Company` позже, в отдельном seller/business flow

## 7. Что уже решено по API и auth-module

### Что оставляем публично в `auth-module`
На текущем этапе публично оставляем только:

- `GET /api/v1/auth/me`

Этот endpoint нужен для того, чтобы по уже валидному Keycloak JWT понять:
- кто сейчас вошёл
- есть ли под этого пользователя локальный `Account`

### Что НЕ оставляем как долгосрочный публичный API
Не считать долгосрочно правильными:

- `signin`
- `refresh`
- `logout`
- `activate`
- `forgotPassword`
- `resetPassword`
- публичный `/me/sync`

### Почему `/me/sync` не считаем целевым API
Потому что синхронизация / создание локального account — это **внутренняя серверная механика**, а не отдельное пользовательское действие.

Правильная идея на будущее:
- публично есть `GET /me`
- внутри backend есть что-то вроде `getOrCreateCurrentAccount(jwt)` для use-case’ов корзины, заказов, профиля и других бизнес-операций
