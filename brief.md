# Market Project — рабочий бриф для новых чатов

## 1. Что это за проект

Это мой Java / Spring Boot multi-module проект, который я хочу довести до уровня **уверенного production-ready backend проекта**, а не просто учебного pet-проекта.

### Текущая идея проекта
Проект похож на e-commerce / market platform и сейчас состоит из нескольких модулей:

- `api-gateway`
- `auth-module`
- `product-service`
- `account-service`
- `eureka-server`
- `common`
- `frontend`
- дополнительные служебные / demo-модули

### Технологии, которые уже используются
- Java
- Spring Boot
- Spring Cloud
- Eureka
- Spring Cloud Gateway
- Spring Security
- JWT
- PostgreSQL
- Redis
- JPA / Hibernate
- Gradle
- Docker Compose
- HTML / JS frontend

---

## 2. Главная цель

Нужно не просто "дописать фичи", а **постепенно превратить проект в полноценный прод-проект**.

Под этим подразумевается:

- стабильная сборка из корня проекта
- единый и чистый Gradle multi-module setup

- безопасная работа с конфигами и секретами

- понятная архитектура сервисов
- хорошие практики безопасности
- тесты
- observability
- CI/CD база
- понятный roadmap развития

## 4. Что уже было выявлено по проекту

### Общая оценка текущего состояния
По задумке проект неплохой и архитектурно амбициозный, но в текущем виде он пока ближе к **сырому pet-проекту с заделом на middle-level**, чем к настоящему production-ready решению.

### Что в проекте уже хорошо
- multi-module структура
- отдельные сервисы
- gateway
- service discovery
- auth логика
- Redis
- email flows
- DTO / mapper / service / repository слои
- в целом правильный вектор мышления

### Основные проблемы, которые уже замечены
- есть недоделанные методы
- есть проблемные / сломанные куски auth-логики
- секреты лежат в `application.yaml`
- используется `ddl-auto`, а не нормальные миграции
- нет полноценной test strategy
- репозиторий засорен лишними файлами (`.idea`, dataSources и т.д.)
- есть признаки распиленного монолита, а не по-настоящему независимых микросервисов
- не выстроен production-level operational контур

## 5. Ключевая стратегия развития проекта

### Главное правило
Не нужно сразу бездумно навешивать сложные технологии ради красивого стека.

Сначала нужно:
1. стабилизировать проект,
2. сделать фундамент,
3. потом усиливать безопасность,
4. потом добавлять более взрослые production-практики.

### Важная идея
Я хочу подключить **Keycloak** для безопасности, но это **не первый шаг**.

Сначала нужно привести проект в состояние:
- он собирается,
- запускается,
- не хранит секреты в репозитории,
- имеет нормальные миграции,
- имеет тестовую базу,
- имеет понятную структуру.

И уже потом делать нормальную интеграцию с Keycloak.

## 6. Целевое состояние проекта

Нужно прийти к архитектуре примерно такого уровня:

- `api-gateway` — единая точка входа
- `keycloak` — identity provider / authentication / authorization
- `account-service` — профиль, настройки, данные пользователя
- `product-service` — каталог, товары, категории
- `postgres` — желательно раздельное владение данными по сервисам
- `redis` — кэш / технические механики / rate limiting / временные данные
- `observability stack` — Actuator, метрики, health checks, логи
- `ci/cd` — build, test, quality gates, docker images

## 7. Roadmap: что нужно сделать, чтобы довести проект до прод-уровня

## Этап 1. Техническая стабилизация проекта
Цель: сделать проект просто стабильно собираемым и запускаемым.

Что нужно сделать:
- привести все модули к одной версии Java
- привести все модули к одной версии Spring Boot
- оставить один Gradle wrapper в корне
- настроить корректный root multi-module build
- переименовать project name во что-то нормальное, если нужно
- удалить мусор из репозитория
- исправить compile errors
- убрать сломанные / недописанные куски
- сделать понятный сценарий локального запуска
- привести `.gitignore` в порядок

### Результат
Проект можно собрать и поднять без ручной магии.

---

## Этап 2. Конфигурация и секреты
Цель: убрать опасные и слабые места в конфигурации.

Что нужно сделать:
- убрать пароли, JWT secret, smtp credentials и прочие секреты из `application.yaml`
- вынести чувствительные значения в env variables / `.env`
- сделать понятные профили (`local`, `dev`, `prod`)
- привести конфиги к аккуратной структуре
- продумать CORS, таймауты, log levels, service URLs

### Результат
Проект становится безопаснее и его можно нормально хранить в git.

---

## Этап 3. База данных и миграции
Цель: сделать БД управляемой и воспроизводимой.

Что нужно сделать:
- отказаться от `ddl-auto: update`
- подключить Flyway
- сделать миграции по сервисам
- продумать границы данных между сервисами
- по возможности не шарить JPA entity между сервисами через `common`
- добавить `@Version` и optimistic locking там, где это реально нужно

### Результат
Схема БД становится контролируемой и предсказуемой.

---

## Этап 4. Безопасность и переход на Keycloak
Цель: уйти от самописного fragile auth-центра к взрослой модели безопасности.

Что нужно сделать:
- встроить Keycloak как внешний identity provider
- перевести gateway в модель resource server
- перевести внутренние сервисы в модель resource server
- перестать развивать самописный refresh token flow как основную auth-модель
- продумать, что делать с `auth-module`
- добавить связку внутреннего пользователя с `keycloak_user_id`
- использовать роли и claims из токена

### Результат
Безопасность становится значительно взрослее и ближе к production-практике.

---

## Этап 5. Авторизация и роли
Цель: сделать не просто login, а корректное управление доступом.

Что нужно сделать:
- определить роли (`USER`, `ADMIN`, `MANAGER` и т.д.)
- внедрить нормальную method security
- реализовать доменные проверки доступа
- четко разделить authentication, authorization и business rules

### Результат
Система доступа становится понятной и управляемой.

---

## Этап 6. Тесты
Цель: перестать бояться рефакторинга и поломок.

Что нужно сделать:
- unit tests на сервисы, мапперы, утилиты
- integration tests через Testcontainers
- API tests на happy path и error cases
- security tests
- позже — тесты на Keycloak integration

### Результат
Проект становится проверяемым, а изменения — безопаснее.

---

## Этап 7. Единый API и обработка ошибок
Цель: сделать контракт API предсказуемым.

Что нужно сделать:
- единый формат ошибок
- единый подход к 400 / 401 / 403 / 404 / 409 / 500
- единый подход к пагинации
- не отдавать entity напрямую наружу
- унифицировать DTO и ProblemDetail / error response

### Результат
Клиентам и frontend проще работать с API.

---

## Этап 8. Надежность и защитные механизмы
Цель: сделать систему устойчивее.

Что нужно сделать:
- таймауты
- retry только там, где это допустимо
- circuit breaker при необходимости
- rate limiting
- ограничения на upload
- валидация файлов
- security headers
- продумать idempotency для критичных операций

### Результат
Проект меньше ломается от внешних сбоев и кривых клиентов.

---

## Этап 9. Логи, метрики, мониторинг
Цель: видеть, что происходит в системе.

Что нужно сделать:
- Spring Boot Actuator
- health / readiness / liveness endpoints
- structured logging
- correlation / request id
- базовые метрики через Micrometer
- позже Prometheus + Grafana
- позже tracing при необходимости

### Результат
Появляется observability и operational visibility.

## Этап 10. CI/CD и инженерная зрелость
Цель: довести проект до инженерно взрослого состояния.
